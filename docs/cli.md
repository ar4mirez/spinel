# CLI and runtime plumbing

What `spinel` does outside the engine: how it runs a file, how it reports itself to Ruby code, and how the small Ruby shims glue the tooling to the VM.

## Subcommands

| command | does |
|---|---|
| `spinel run <file> [args]` | run a file on the VM with the project's gems visible |
| `spinel run -e CODE`, `spinel run -I DIR app.rb`, … | `ruby`'s command line (the row below), with the project's gems visible as `spinel run` makes them: `shims/setup.rb` runs first. Any first word after `run` that starts with `-`, other than `run`'s own `--watch`, `--dump-bytecode`, `--strict-ruby-version` and `--`, means this form. |
| `spinel run --watch <file> [args]` | run it again whenever the project changes; see `--watch` below |
| `spinel run --dump-bytecode <file>` | compile the file and print its bytecode instead of running it; see below |
| `spinel <file.rb>` | same as `run`. Subcommand names win: `spinel install` is the subcommand even if `install` exists as a file; use `spinel run install` or `spinel ./install` for the file. Words after the file are its `ARGV`, even one that names a subcommand: `spinel app.rb x` passes `x` to `app.rb`. |
| `spinel -e CODE`, `-r LIB`, `-I DIR`, `-w`, `-v`, … | `ruby`'s command line, parsed as `ruby.c`'s `proc_options` parses it: `-e`, `-r`, `-I`, `-w`/`-W[level]`/`-W:category`, `-v`, `-d`, `-n`/`-p`/`-l`/`-a`/`-F`, `-i[ext]` (in-place editing through `ARGF`, #41), `-0[octal]`, `-s`, `-x[dir]`, `-C dir`, `-c`, `-E`, and `-` for a program on standard input; `RUBYOPT`, `RUBYLIB` and, for `-S`, `RUBYPATH` are read as `ruby` reads them (#314). Of the `--enable`/`--disable` features, `gems`, `did_you_mean` (see "What every program starts with"), `rubyopt` and `frozen-string-literal` act; a feature may be named as `ruby` reads it, in any case and with each `-`/`_`-separated part shortened to a prefix (`--disable=gem` is `gems`, `--disable=d-y-m` is `did_you_mean`). The rest (`error_highlight`, `syntax_suggest`, the JITs) are accepted and do nothing. Any first word that starts with `-`, other than `-h`, `--help` and `-V`, means this form; a flag `ruby` does not have is its `invalid option` error (#62). |
| `spinel x [--source URL] [--gem GEM] <gem>[@req] [args]` | run a gem's executable from a GEM_HOME of its own under `~/.spinel/x/`, project untouched; see `spinel x` below |
| `spinel init` | in the current directory: Gemfile, `.ruby-version` containing `spinel-<version>`, `test/`, `.gitignore` entry for `.spinel/`. Never overwrites: an existing Gemfile, `.ruby-version` or `test/` is kept as it is, and an existing `.gitignore` gets the `.spinel/` line appended only when no line already names `.spinel` (with or without slashes, or negated). Prints one line per path saying whether it was created, appended to, or already existed. |
| `spinel install/add/remove/update` | package-manager.md |
| `spinel test [-j N] [FILE[:LINE]...]` | run `test/**/*_test.rb` on `N` forked workers (the physical cores by default), `test/test_helper.rb` loaded once before the fork; `spec/**/*_spec.rb` after them the same way, `rspec/core` and `spec/spec_helper.rb` loaded once, each worker running its files' examples through RSpec's runner (#837), and reporting each test or example as a JSON event (#93; `SPINEL_TEST_EVENTS` names a file that gets them). Files given run instead, `FILE:LINE` only the test or example there. Prints dots, each failure with gem frames folded, a summary and a `spinel test file:line` command to re-run each failure; exits 1 on any failure (#94); test-runner.md |
| `spinel build` | build.md |
| `spinel parse <file>` | print the `spinel_ast` tree for one file; `--format debug` for the derived `Debug`. Exits 1 on a syntax error, 2 if the file cannot be read. |
| `spinel parse <dir>` | lower every `.rb` file under a directory and report only what failed. Exits non-zero on an unhandled node, never on a syntax error, because a corpus may legitimately contain invalid Ruby. This is the check behind the `sweep` CI job. |
| `spinel spec [dir]` | run ruby/spec (development only, hidden from `--help` in release builds) |
| `spinel index [--source URL] [--names] [gem...]` | bring the compact index cache up to date: `/versions`, `/names` with `--names`, `/info/<gem>` for each gem named; prints the cache directory, then one line per file (`fetched N bytes`, `appended N bytes`, `not modified`, `current`, `not in the index`). The debugging window onto the index client (package-manager.md, "Index client"); hidden from `--help`. Exits 1 if any request failed. |
| `spinel fetch [--source URL] [--gem-home DIR] <name@version[-platform]>...` | fetch gems into the global store: brings the index up to date, takes each gem's checksum from its `/info` line, and prints the store directory, then one line per gem (`fetched N bytes` or `in the store`, with its entry). With `--gem-home`, once every gem is stored, links them into `DIR` as `gem install` lays out a GEM_HOME and removes what an earlier link made for gems not named, then prints `gem home: DIR` and one line per gem (`linked`, `current` or `removed`). The debugging window onto the store and the GEM_HOME (package-manager.md, "Global store"); hidden from `--help`. Exits 1 if any gem failed, 2 for a gem it cannot parse. |
| `spinel pack <payload> -o <app>` | write a compiled app (build.md, "Format") from a payload file and this `spinel`: appended with its trailer on Linux, in the `__SPINEL,__payload` section and signed again ad hoc with `codesign` on macOS. Hidden: `spinel build --compile` (#100) is the command that makes apps. |

## What `spinel run` sets up

Before user code, and before any `-r` file, the VM runs the embedded `shims/setup.rb`. `spinel run` and `spinel <file>` run it; `ruby`'s command line (`spinel -e`, `spinel -w app.rb`) does not, as `ruby` looks for no project.

1. Walk up from the current directory to find `.spinel/gem_home/`. If found, set `GEM_HOME` and `GEM_PATH` to it, as `bundle exec` does for a `BUNDLE_PATH`, and put its `bin/` first on `PATH` (once, so a nested `spinel` does not grow it). They are set in the environment, so child processes see the same gems and executables; RubyGems reads them when it first needs its paths, and a `Gem` already loaded is told with `Gem.paths=`. The setup runs before RubyGems loads, so RubyGems starts with the project's paths. Outside a project nothing changes.
2. Load `.spinel/require_map.bin` if present (see below).
3. Register the bytecode cache directory, `.spinel/bytecode/` beside the gem home (#40), so `require` reads and writes it. Outside a project there is none, and nothing is read or written.

## What every program starts with

`ruby` runs `gem_prelude.rb` before every program, and so does Spinel, as `shims/gem_prelude.rb` (#319): after `shims/setup.rb` when that runs, after `-I`, `RUBYLIB` and the flags that set globals, and before any `-r` file, which is where `ruby` runs it. The CLI first defines `Gem` and `DidYouMean` as empty modules, as `ruby.c` does, for the features the command line leaves on; the shim then requires `rubygems` (and `bundled_gems` after it) and `did_you_mean`.

- `--disable-gems` (or `--disable-all`, or, on `ruby`'s command line, `RUBYOPT=--disable-gems`; `spinel run` does not read `RUBYOPT`) leaves both undefined: as in `ruby`, `did_you_mean` is only loaded with RubyGems. `--disable=did_you_mean` leaves only it out.
- A library that cannot be loaded, as when the stdlib could not be extracted, is a warning on stderr (`` `RubyGems' were not loaded.``) and the program runs; `Gem` is then the empty module.
- RubyGems' own `Kernel#require` and `Kernel#warn` are in place from then on, as in `ruby`.
- Not yet: CRuby's prelude also loads `error_highlight` and `syntax_suggest/core_ext`; Spinel does not, so `--enable` naming them changes nothing.
- What it costs: `spinel -e 0` takes about 1.7 times as long as with `--disable-gems`; the PR for #319 has the numbers.

RubyGems finds its directories in `RbConfig::CONFIG`. Spinel installs nothing beside its binary, so `prefix` is the Spinel home (`$SPINEL_HOME`, else `~/.spinel`) and the rest are laid out under it as CRuby lays them out under its prefix: `Gem.default_dir` is `~/.spinel/lib/ruby/gems/4.0.0`, and `sitelibdir`, `~/.spinel/lib/ruby/site_ruby/4.0.0`, is on `$LOAD_PATH` just before the stdlib. Both carry `@gem_prelude_index`, as `ruby.c` marks its default entries, and `Gem.load_path_insert_index` is the first marked entry, so gems RubyGems activates go after `-I`. `RbConfig::TOPDIR` is the prefix, the Spinel home. `rubylibdir` is the extracted stdlib. A project's gems come from its `.spinel/gem_home/` (above), not from these.

Bin stubs in `.spinel/gem_home/bin/` start with `#!/usr/bin/env spinel` and call `Gem.activate_bin_path`, the same shape RubyGems generates. A program whose first line is a `#!` naming neither `ruby` nor `spinel` starts at the first later `#!` line naming one, as if `-x` had been given: CRuby looks for its engine's name, and Spinel looks for both its own and `ruby`'s, so stubs and scripts written for `ruby` both run. `Gem.ruby` returns the absolute path of the running `spinel` binary so anything that spawns "the current Ruby" spawns Spinel.

## `spinel x`

`spinel x rubocop --version` runs a gem's executable without installing it into the project (#68), as RubyGems' `gem exec` and uv's `uvx` do. `crates/spinel-cli/src/x.rs` puts `spinel install`'s pieces in a different order: no Gemfile and no lockfile, and nothing read from or written to the current directory.

- **Arguments.** The first word is the gem, and the executable to run from it; `@` then a requirement narrows the version, as `gem exec`'s `name:version` does: `rubocop@1.60.0` is `= 1.60.0`, `rubocop@~> 1.60` and `rubocop@>= 1.60, < 2` are `Gem::Requirement`s, several separated by commas as a `gem` line lists them. Every word after it is the executable's `ARGV`, `--help` included; `spinel x`'s own options (`--source`, `--gem`) come before it. `--source URL` is the compact index to resolve against and fetch from, rubygems.org by default.
- **Resolution.** Every run resolves the gem afresh, as `gem exec` does without `--conservative`: the index is brought up to date (a `not modified` per file when nothing changed), and an unpinned gem is its newest version. The resolver is `spinel install`'s, for the local platform, Spinel's Ruby and the RubyGems it ships. A gem the index does not have, or no version of it meeting the requirement, is `could not find a valid gem 'NAME' (REQ) in SOURCE`, exit 2, `gem exec`'s status for it; a conflict deeper down is the resolver's explanation, rooted at `spinel x`, also exit 2.
- **The GEM_HOME.** The gems are fetched into the global store and linked, as `spinel install` links a project's (package-manager.md, section 5), into `<spinel home>/x/<gem>-<version>-<key>/`, the key the first 16 hex digits of the SHA-256 of every resolved gem's full name and `.gem` checksum. So the directory is named by what was resolved, as uv names a cached tool environment: a second run that resolves to the same gems, whatever requirement it was given, fetches nothing, writes nothing and prints nothing of its own; a newer version is another directory beside it. A first run prints `+ gem version` for each gem it linked, on standard error, so standard output is the command's alone. Nothing removes old directories yet: `// ponytail:` none is pruned; the upgrade is a `spinel cache clean`, or an age limit.
- **Which executable.** As `gem exec`'s `load!` chooses: among every gem resolved, the ones with an executable named like the first word, narrowed to the gem of that name when it is one of them (`spinel x rspec` runs `rspec-core`'s `rspec`); with none, the gem's only executable when it has exactly one (`haml_lint`'s `haml-lint`). Two gems with it, a gem with several and none named so, or one with none, is `gem exec`'s error, exit 1. `--gem GEM` names the gem when the executable is named otherwise, as `gem exec -g` does: `spinel x --gem rspec-core rspec`, and the requirement after `@` is then the gem's.
- **Running it.** The bin stub `link` wrote in the GEM_HOME's `bin/` replaces the `spinel x` process (`exec`); when another gem resolved has an executable of the same name and `link` gave `bin/` to that one, the chosen gem's own stub is written once to `x-bin/<gem>/<executable>` in the GEM_HOME and run instead. Either way the stub replaces the process, so the exit status, signals included, is the command's. The GEM_HOME is the whole of `GEM_HOME` and `GEM_PATH` and its `bin/` is first on `PATH`, as `spinel run` sets them for a project; the stub runs as `ruby`'s command line runs a script, `spinel -- <stub>`, so `shims/setup.rb` does not replace them with the current directory's `.spinel/gem_home/`. The current directory is the command's, as it is for `gem exec`.
- **Differences from `gem exec`.** It installs into a GEM_HOME of its own per resolution rather than into `Gem.dir`, so it never adds to the user's gems, which is what `uvx` does; there is no `--conservative`, since the cache already reuses what an unpinned run resolved to while the index has nothing newer; no `--pre` (a requirement naming a prerelease allows them, as in a Gemfile); and `:` does not separate the requirement. Native extensions are not built, as for `spinel install`: a gem that needs one is linked with a warning and RubyGems will not activate it, which today stops `spinel x rubocop` at `json`: `spinel install` substitutes the built-in gems (#83), and `spinel x` does not yet.
- **Checked by** `crates/spinel-cli/tests/x.rs`, against gems `tests/fixtures/x/build.sh` builds with `gem build`, served with a compact index on 127.0.0.1: the newest version with its dependency and the arguments passed through, run from a project whose Gemfile, lockfile and `.spinel/gem_home/` are byte for byte the same afterwards; the second run fetching and writing nothing; `gem@1.0.0`, `gem@~> 1.0` and `gem@< 2, >= 1` sharing one GEM_HOME; the exit status; an unknown gem and an unmet requirement; each way the executable is chosen; and a dependency with an executable named like the gem's, where the gem's own runs.

## Bytecode cache and require map

- `.spinel/bytecode/<sha256 of source>.sbc` holds compiled bytecode (#40, `crates/spinel-vm/src/sbc.rs`). `require`, `require_relative` and `load` check it before parsing a file from disk, and write it after compiling one. The format is position-independent: symbols are stored by name and relinked on load, so a cache file is valid across processes and Ractors; what a read gives back is the same immutable, `Send + Sync` `Iseq` the compiler makes.
  - A file is used only when its header matches: the format, a fingerprint of the compiler (a hash, made by `crates/spinel-vm/build.rs`, of the sources of `spinel-vm`, `spinel-parse`, `spinel-ast` and `spinel-regex`, of `spinel-core`'s parse hook, and of `Cargo.lock`), the source's hash, the path the source was compiled under — `__FILE__`, `__dir__` and backtraces carry it — and the `frozen_string_literal` setting. Then the payload's length and SHA-256 are checked, and the payload is decoded with every length and tag checked. Anything else — another build's file, a truncated or corrupted one — is parsed past as if there were no cache, and overwritten.
  - The parser's warnings about the file are kept in the entry and given again on a hit, so a run with the cache prints what a run without it prints. A file that does not parse, or that the compiler refused part of, is never written.
  - Writes go to a temporary file in the same directory and are renamed into place, so processes sharing a cache never read half a file. A file that cannot be written is a slower next run, never an error.
  - The main script, `-e` and standard input are compiled every time, so `--dump-bytecode` and syntax errors in them read as before; and a file shipped inside the binary is not the project's to cache.
  - `// ponytail:` two files with the same bytes at different paths share one cache file name, and each run that loads both rewrites it for the other. The upgrade, if a project shows it, is the path's hash in the name.
- `.spinel/require_map.bin` (#66, `crates/spinel-vm/src/require_map.rs`) lists every directory under every installed gem's `require_paths` and under the stdlib: what each one held when `spinel install` last ran. `require` still walks `$LOAD_PATH` in its order as it is when it looks; for an entry the map lists, the map says whether the file is there, so an entry that does not have it is passed over and one that does is taken, with no look on disk. Every other entry — the program's own, `-I`, `RUBYLIB`, a gem installed some other way — is looked at on disk as before, and `$LOADED_FEATURES` is asked first as before. The map is a cache of directory listings rather than of feature names, because which entry has a feature first depends on the load path the program makes; this way the map cannot change the answer, only how fast it comes.
  - A directory's listing is used only if the directory is as it was: the map keeps each one's device, inode, and modification and change times, and a directory is looked at the first time a process asks about it and again on every answer that it does not have a file, and passed to the look on disk for good once any of them moved. Adding, removing or renaming a file changes them, and so does replacing the directory. A directory whose times are within a tick of when it was listed (git's "racily clean" case: 100 ms where times have nanoseconds, 2 s where they do not) is listed again on that first look and used only if the listing is the same; `spinel install` waits up to 250 ms for just-made directories to stop being racy.
  - A name the map does not have counts as absent only if it is ASCII and no entry has it in another case, since a case-insensitive file system (macOS's default) opens `Foo.rb` as `foo.rb`. A symlink in a gem's directory is looked at on disk. The file is checked as a cache file is: format, length and SHA-256 of the payload, then every length, kind and index as it is read; a map that fails any of them is not used.
  - `spinel install` writes it every time, with `--frozen` too (package-manager.md, section 7); the hidden `spinel require-map <file> [dir...]` writes one for the stdlib and the directories given, which is how a GEM_HOME made some other way, `bench/require_map.rb` and `crates/spinel-cli/tests/require_map.rs` get one. `crates/spinel-cli/tests/install.rs` checks that install writes it and programs use it.

## How Spinel identifies itself

| constant | value |
|---|---|
| `RUBY_ENGINE` | `"spinel"` |
| `RUBY_ENGINE_VERSION` | Spinel's own version, e.g. `"0.3.0"` |
| `RUBY_VERSION` | the Ruby language version Spinel implements, `"4.0.0"` at launch. This drives ruby/spec's `ruby_version_is` guards and gems' version checks. |
| `RUBY_PLATFORM` | the host triple as RubyGems spells it, e.g. `"arm64-darwin24"` |
| `RUBY_PATCHLEVEL` | `-1` |
| `RUBY_RELEASE_DATE`, `RUBY_COPYRIGHT`, `RUBY_DESCRIPTION` | Spinel's |

Ruby 4.0's `Ruby` module holds the same objects (`Ruby::VERSION.equal?(RUBY_VERSION)`). Like CRuby, Spinel fixes `RUBY_PLATFORM` when it is built (`crates/spinel-vm/build.rs`), and `RbConfig::CONFIG["arch"]` repeats it, which is what `Gem::Platform.local` parses.

Reporting `"spinel"` rather than `"ruby"` is honest and is what JRuby and TruffleRuby do. It costs nothing for `platforms :ruby`: Bundler's `CurrentRuby#ruby?` answers true on any engine whose generic local platform is `ruby`, every platform but Java and Windows (`generic_local_platform_is_ruby?`, in Bundler since 2.1, rubygems commit 59752dd85), so stock `require "bundler/setup"` running on Spinel loads `platforms :ruby` gems, and `ruby_40` ones, without help. `mri?` needs RUBY_ENGINE `"ruby"`, so `platforms :mri` gems are left out on Spinel, as on TruffleRuby. Spinel's own Gemfile evaluation answers each platform name as that Bundler does on Spinel (`GemfileDependency#current_platform` in `crates/spinel-cli/src/resolver.rs`): `ruby`, and `ruby_NN` only for the language version Spinel implements, so `spinel install` installs exactly the gems `bundler/setup` then loads. A change adding `spinel` to `CurrentRuby`'s engine list was planned, opened upstream as https://github.com/ruby/rubygems/pull/10070, and withdrawn once this was measured: it changes nothing where Spinel runs, and so neither does a warning for gems it would skip (#72). `crates/spinel-cli/tests/bundler_setup.rs` checks both halves on `fixtures/bundler-platforms`.

**Language version.** Spinel implements one Ruby language version at a time, the latest stable, and follows Ruby's December releases. `ruby "3.3"` in a Gemfile and a `.ruby-version` that names a CRuby version are read and produce a warning, never an error, because the intent is "this app expects at least that Ruby". `--strict-ruby-version` turns the warning into an error for CI.

- Who reads them: `spinel run` and `spinel <file>`, before the program starts. Only `run` takes `--strict-ruby-version`, which exits 1 without running anything. `ruby`'s command line (`spinel -e`, `spinel -w app.rb`) reads neither, as `ruby` does not.
- Where: the nearest `.ruby-version` and the nearest `Gemfile`, each looked for from the current directory upward. Each request that is not met is one line on stderr naming the file.
- `.ruby-version`, first word: `spinel-<version>` (what `spinel init` writes) is met by this Spinel or a later one; `<version>` or `ruby-<version>` is a CRuby version, met when `RUBY_VERSION` is that version or later; bare `spinel` or `ruby` is always met. Any other word, such as `jruby-9.4` or `ruby-head`, is not.
- Versions compare as RubyGems compares them (`Gem::Version`): a prerelease such as `4.0.0-preview1` or `4.0.0.rc1` comes before `4.0.0`. `3.3.0p0` is a prerelease of `3.3.0` the same way. A `.ruby-version` word RubyGems would reject, as version managers write them (`2.7.8_1`, `ruby-3.3.0@gemset`), is read by its leading numbers (`2.7.8`, `3.3.0`); only the Gemfile's `ruby` line follows Bundler in rejecting it, so such a requirement there is not met.
- Gemfile: the quoted requirements of a `ruby` line, each read as a minimum, so `ruby "~> 3.3.0"` and `ruby ">= 3.1", "< 5"` are met by Ruby 4.0. Upper bounds and `!=` are passed over, and keyword options (`engine:`, `file:`) are not read. The Gemfile is scanned line by line, not evaluated, so a version computed at runtime is not seen.

## `--dump-bytecode`

`spinel run --dump-bytecode file.rb` is to the compiler what `spinel parse` is to the tree. It compiles the file and prints its `Iseq` in Rust's `Debug` form, without running it: the instructions, one per `pc`, with the literal and symbol pools, the locals, the call sites and the nested bodies (`children`). A file that does not parse reports its syntax errors and exits with the status `spinel run` gives them.

The format is the instruction set's, and it changes when the instruction set changes; `CHANGELOG.md` records each change. A superinstruction (engine.md, Bytecode) prints as a struct named for the instructions it stands for, with their operands as fields:

```
GetLocalPushIntBinOp {
    slot: 0,
    int: 2,
    op: Lt,
},
PushInt(
    2,
),
BinOp(
    Lt,
),
JumpUnless(
    3,
),
```

The instructions after it are the ones it stands for, still in place. A jump into the middle of the run lands on them, and they are what runs when the superinstruction declines. Each line is one `pc`: read the stream with nothing skipped, and a jump's displacement counts every line.

## `--watch`

`spinel run --watch app.rb [args]` runs the program, and runs it again whenever the project changes. `spinel test --watch` is to do the same once the test runner exists, with #97 choosing the tests a change affects; the supervisor, `crates/spinel-cli/src/watch.rs`, takes any `spinel` command line to restart.

- **Watched:** the current directory and everything under it, through the `notify` crate (inotify on Linux, FSEvents on macOS). Run it from the project's root.
- **A change:** a file or directory created, written, renamed or removed, or its metadata changed. Reading is not, as every run reads the program.
- **Not a change:** a path `.gitignore` excludes, as git decides it: the `.gitignore` files in the directory and its subdirectories, the nearest first, then `.git/info/exclude`, then the user's global excludes file (`core.excludesFile`, else `~/.config/git/ignore`). A path under an excluded directory stays excluded, `.git/` never counts, and an edited `.gitignore` is read again. A `.gitignore` above the current directory is not read.
- **Debounce:** a restart waits until 100 ms pass with no further change, so one save an editor writes in several steps restarts the program once.
- **Restart:** the program runs as a child `spinel run`, without `--watch`, in a process group of its own. A restart sends that group SIGTERM, then SIGKILL to whatever is left after two seconds, and starts a fresh child; nothing is reloaded in place, as Zeitwerk and similar already do that inside the app. Each restart is one line on stderr naming what changed, such as `spinel: restarting: config/settings.rb changed`. The child reads `.ruby-version` and the Gemfile itself, so each run reports a mismatch afresh.
- **A program that ends** on its own is reported, as in `spinel: the program exited with status 1; waiting for a change`, and the next change starts it again.
- **Ctrl-C**, SIGTERM or SIGHUP end the program's group the same way, then `spinel`, which exits with 128 plus the signal's number: 130 for Ctrl-C.
- **Not yet:** the program's group is not the terminal's foreground group, so a program that reads from the terminal is stopped (SIGTTIN) rather than handed it; standard input from a pipe or a file works. One recursive watch covers ignored directories too, whose events are then dropped, so a very large ignored tree can reach the inotify watch limit.

## Bundler running on Spinel

Apps call `require "bundler/setup"` in their own boot files, so Bundler the gem must run on Spinel and read Spinel's `.spinel/gem_home` and `Gemfile.lock`. Bundler is pure Ruby, and the GEM_HOME layout is standard, so this is a compatibility test rather than new code: `crates/spinel-cli/tests/fixtures/bundler-setup` boots an app through `bundler/setup` with `BUNDLE_PATH` pointed at `.spinel/gem_home`. `spinel install` writes `.bundle/config` with `BUNDLE_PATH: ".spinel/gem_home"`, as `bundle config set --local path .spinel/gem_home` writes it (#71).

- **Where Bundler reads that path.** Bundler reads an explicit path's gems not from the path itself but from `<path>/<RUBY_ENGINE>/<RbConfig ruby_version>` (`Bundler.ruby_scope`), and refuses `path.system` beside it. So `spinel install` also makes `.spinel/gem_home/ruby/4.0.0/`, where CRuby 4.0's Bundler reads, and `.spinel/gem_home/spinel/4.0.0/`, where Bundler running on Spinel reads. Each holds one relative symlink per GEM_HOME subdirectory (`gems -> ../../gems`, `specifications`, `extensions` and the rest of `Gem::REPOSITORY_SUBDIRECTORIES`), so every reader sees the one GEM_HOME, and a gem plain `bundle install` puts there lands in it too.
- **Each engine runs gem executables on itself.** `bin/` is the exception, as `bundle exec` puts `<path>/<scope>/bin` first on `PATH` and execs the stub it finds there. `.spinel/gem_home/bin/` holds the stubs that start `#!/usr/bin/env spinel`, and `spinel/4.0.0/bin` links to it. `ruby/4.0.0/bin/` is a directory of its own, holding for each of those the stub CRuby's RubyGems writes with `--env-shebang`, byte for byte: the same text starting `#!/usr/bin/env ruby`. `spinel install` keeps it in step with the GEM_HOME's `bin/`, writing a stub for each executable added and removing such a stub once its gem is gone from the GEM_HOME; a stub CRuby's own `bundle install` wrote for a gem still there, and any other file, is left alone. So plain `bundle exec rake` runs rake on CRuby, and Bundler running on Spinel runs it on Spinel. The scope itself is not a symlink to the GEM_HOME, since that would be a cycle. Something already there that is not such a symlink, such as a directory plain Bundler made before `spinel install` ran, is left alone with a warning. A CRuby of another minor version reads another directory (`ruby/3.4.0`) and does not see these gems, as it would not see gems `bundle install` put there for 4.0.
- **Bundler's executable.** `Bundler.setup` records the `bundle` executable in `BUNDLE_BIN_PATH` and raises when it finds none. It looks for `exe/bundle`, then `libexec/bundle`, beside the directory its `lib` was loaded from, then the default gem's. Spinel's stdlib carries ruby/ruby's `libexec/bundle` (`stdlib/libexec/`, vendored with the rest), and extracts it to `~/.spinel/stdlib/<version>-<digest>/libexec/` beside the library's `lib/`, as ruby/ruby's tree has them.
- **Checked by** `crates/spinel-cli/tests/bundler_setup.rs`. `spinel install` installs the fixture's lockfile, and its `app.rb` boots under `spinel run` through `bundler/setup` with exactly the locked gems on the load path. With `SPINEL_CRUBY_BUNDLER` set and CRuby 4.0's `bundle` on `PATH` (CI's Linux job sets both), CRuby's own `bundle check` and `bundle exec ruby app.rb` in the same project find the same gems. For gem executables, `fixtures/plain` (rake) is installed and `bundle exec rake` runs rake on Spinel under Bundler running on Spinel; with CRuby, plain `bundle exec rake` runs it on CRuby, and `ruby/4.0.0/bin/rake` is the stub `gem install --env-shebang` writes.
