# Package manager

Goal: `spinel install` on a real `Gemfile.lock` finishes in seconds, produces a GEM_HOME that `bundle exec` would also accept, and never asks the user for a C compiler.

The package manager is Rust in `spinel-cli`. The only Ruby it runs (Gemfile and gemspec evaluation, bin stubs) runs on Spinel's VM, which is why it lands in phase 4.

## Compatibility contract

| Artifact | Spinel behavior |
|---|---|
| `Gemfile` | Read. Evaluated as Ruby on Spinel's VM, never parsed by hand. |
| `Gemfile.lock` | Read and written. Bundler must accept Spinel's output and vice versa. |
| `.ruby-version` | Read. |
| `GEM_HOME` layout (`specifications/`, `gems/`, `extensions/`, `bin/`) | Written to `.spinel/gem_home/`. Standard, so `Gem::Specification`, `Bundler.setup`, and every gem-aware library work unchanged. |
| `~/.gem`, `~/.bundle/config` | Ignored, but for a source's credentials, read from the project's `.bundle/config`, the `BUNDLE_*` environment and the global config as Bundler reads them (section 2). `BUNDLE_GEMFILE` env var is honored. Mirrors (`bundle config mirror`) in phase 5. |
| `ruby "x.y"` directive | Read, warns on mismatch. See cli.md, "Language version". |

## Pipeline

```
Gemfile ──(ruby: gemfile_eval.rb)──▶ deps JSON ──▶ resolver ◀── compact index (cached)
                                                       │
                                     Gemfile.lock ◀────┴────▶ install plan
                                                                  │
                                    global store ◀── fetch .gem ──┤
                                                                  ▼
                                                        .spinel/gem_home/ (links) + ext download + bytecode warm + require map
```

### 1. Gemfile evaluation

`shims/gemfile_eval.rb` defines a small `Bundler::Dsl`-shaped object (`source`, `gem`, `group`, `platforms`, `git`, `path`, `ruby`, `gemspec`, `eval_gemfile`, and the rest of Bundler 4's DSL: `platform`, `github`, `git_source`, `install_if`, `env`, `plugin`) and prints JSON. Evaluating it as Ruby means every Gemfile that Bundler accepts, Spinel accepts, including the ones with `if ENV[...]` logic. Do not try to parse Gemfiles with Prism.

`spinel run shims/gemfile_eval.rb` evaluates `BUNDLE_GEMFILE` when it is set and not empty, otherwise the nearest `gems.rb` or `Gemfile` from the current directory upward, as Bundler finds it. Each method records what `Bundler::Dsl` records and rejects what it rejects, with Bundler's message: a Symbol gem name, an unknown platform, the same gem twice with different requirements or sources, a `branch` without a git source, `git` or `path` without a block, a second global `source`, an undefined method. An error prints `There was an error parsing \`<file>\`: <message>` and `  from <file>:<line>` on stderr and exits 1; a gem listed twice alike is Bundler's warning on stderr and both entries stay. The one rule it does not copy is Bundler's rejection of an unknown `gem` option: those are kept, in `options`, for the resolver to judge. `crates/spinel-cli/tests/gemfile_eval.rs` checks every method against fixtures whose dependency lists match Bundler 4.0.20's `Bundler::Dsl`.

The JSON is pretty-printed, keys always in the order below and always present (`null` when unset); arrays keep declaration order.

```json
{
  "gemfiles": ["/abs/Gemfile", "/abs/gemfiles/common.rb"],
  "source": {"type": "rubygems", "remote": "https://rubygems.org", "cooldown": null},
  "ruby": {"versions": ["3.4.1"], "engine": "ruby", "engine_versions": ["3.4.1"], "patchlevel": null},
  "optional_groups": ["ci"],
  "gemspecs": [{"path": ".", "root": "/abs", "files": ["/abs/app.gemspec"], "name": null, "glob": null,
                "development_group": "development", "gemfile": "/abs/Gemfile"}],
  "dependencies": [
    {"name": "pg", "requirements": ["= 1.5.0.pre.rc1"], "groups": ["default"], "platforms": [],
     "source": null, "require": [], "install_if": true, "env": null, "force_ruby_platform": null,
     "gemfile": "/abs/Gemfile", "options": {}}
  ]
}
```

- `gemfiles`: every file evaluated, the Gemfile first, then each `eval_gemfile` (resolved against the directory of the file that calls it), absolute.
- `source`: the global rubygems source, or `null` when the Gemfile names none. `remote` is as written; Bundler compares remotes with a trailing `/`. `cooldown` is `source`'s `cooldown:` option.
- `ruby`: the `ruby` directive as Bundler's `RubyVersion` holds it, or `null`. `versions` are requirements with `=` dropped and `-` read as `.`; `file:` reads the version from the named file, in `.ruby-version` or `.tool-versions` form, relative to the file with the directive. `engine` defaults to `ruby`, `engine_versions` to `versions`, and `patchlevel` is `"-1"` for a prerelease Ruby.
- `optional_groups`: groups declared with `optional: true`.
- `gemspecs`: each `gemspec` directive, with the gemspec files it found in `path` (relative to `root`, the directory of the file that has the directive). `spinel install` evaluates each into its gem, from a path source, and its development dependencies, in `development_group` (section 12).
- `dependencies`: one per `gem` call that ran.
  - `requirements`: `Gem::Requirement#as_list`, so `"1.0-rc1"` is `"= 1.0.pre.rc1"` and no requirement is `[">= 0"]`.
  - `groups`: the enclosing `group` blocks then the gem's `group:`/`groups:`; `["default"]` when there are none.
  - `platforms`: the enclosing `platforms` blocks then the gem's `platform:`/`platforms:`, each one of Bundler's platform names.
  - `source`: `null` for the global source. Otherwise the gem's own `path:`, else its `git:` or git-source option (`github:`, `gitlab:`, one from `git_source`), else its `source:`, else the enclosing `source`, `git`, `github` or `path` block. One of `{"type": "rubygems", "remote", "cooldown"}`, `{"type": "git", "uri", "branch", "ref", "tag", "submodules", "glob"}`, `{"type": "path", "path", "root", "glob"}` (`path` as written, relative to `root`), or `{"type": "plugin", "plugin", "uri", "options"}` for `source "...", type: ...`.
  - `require`: `null` when not given (require the gem's name), else Bundler's autorequire list: `require: false` is `[]`.
  - `install_if`: the enclosing `install_if` conditions and the gem's `install_if:`, evaluated now, as Bundler does.
  - `env`: the enclosing `env` block's variable name (or Hash, with a Regexp written as its `inspect`), else `null`; Bundler checks it at install time, and so should Spinel.
  - `force_ruby_platform`: as given, else `null`.
  - `gemfile`: the file the `gem` call is in.
  - `options`: every other option, keys as strings.

### 2. Index client

rubygems.org's compact index, the same API Bundler uses:

- `GET /versions` – append-only list of every gem and version, ETag + `Range` for incremental updates. Cached at `~/.spinel/index/<host>/versions`.
- `GET /info/<gem>` – one line per version: `version[-platform] dep:req,dep:req|checksum:sha256,ruby:>= 3.0,rubygems:>= 3.3`.
- `GET /names`

Fetched with `reqwest`, concurrent (limit 32), ETag-validated. Private sources (`source "https://gems.example"`) use the same API; fall back to the legacy `specs.4.8.gz` only if compact index returns 404. Git and path sources are resolved by cloning or reading the directory and evaluating the gemspecs (section 12).

The client is `crates/spinel-cli/src/compact_index.rs`, and it updates each file as Bundler 4's `CompactIndexClient::Updater` does:

- **Cache layout.** `<home>/index/<host>/` (`<home>` is `$SPINEL_HOME`, else `~/.spinel`; a source on a port other than its scheme's adds `:<port>`, and one under a path adds `-` and 16 hex digits of the path's SHA-256, so two sources never share a cache). In it: `versions`, `versions.etag`, `names`, `names.etag`, `info/<gem>`, and `info-special-characters/<gem>-<md5 of name>` for a name with anything but lowercase letters, digits, `_` and `-`, as Bundler lays them out. A gem name outside rubygems.org's `[A-Za-z0-9._-]` is refused rather than made into a path. Every file is written beside itself and renamed into place.
- **Incremental update.** With a non-empty cached copy, one request: `Range: bytes=<size - 1>-` (one byte back, so the range is never empty) and `If-None-Match` with the stored ETag. A 304 keeps the copy. A 206 is appended without its first byte and kept only when the whole result matches the SHA-256 in `Repr-Digest` (else `Digest`; as a byte sequence, a quoted string as rubygems.org sends it, or bare base64). With no digest nothing is appended, as in Bundler: appending unverified is too error prone. A 200, a server ignoring the range, replaces the copy.
- **Fallback.** No cached copy, a 206 with no digest or a mismatch (a stale or corrupt cache), or a 416 (a cache longer than the file now is): fetch the whole file, with the ETag but no range. A whole file whose digest does not match is an error and is not written. Two differences from Bundler, both toward refetching: with no cached copy no ETag is sent (Bundler's would get a 304 and keep nothing), and a response with no ETag removes the stored one rather than leaving it to vouch for a file it was not sent with.
- **`/info` skip.** An `/info/<gem>` is requested only when its cached file's MD5 differs from the checksum the cached `/versions` lists last for the gem, so a warm cache costs one request (the `/versions` 304) however many gems are asked for. A gem `/versions` does not list is not requested. That request carries no ETag, and none is stored for `/info`: the copy is already known to differ from the server's, and rubygems.org's ETag for an info file is its MD5, so a stored one still current would get a 304 that keeps the wrong copy on every run (Bundler sends it). Without one, a truncated copy is completed by the range and any other is fetched again.
- **Concurrency.** At most 32 requests in flight per client: a permit covers one file's update, which makes at most one request at a time.
- **What a 304 vouches for.** A 304 carries no digest, so a cached `/versions` or `/names` damaged after it was written, with its ETag still current, is trusted until the file changes upstream, as it is by Bundler. The cache's own writes cannot leave one: the data is renamed into place before its ETag is written.

- **Private sources** (#89, `crates/spinel-cli/src/credentials.rs`). A source's credentials are those in its URL (`https://user:secret@gems.example`), else `Settings#credentials_for`'s: the setting for the source's URL, then for its host (`BUNDLE_GEMS__EXAMPLE`, as `bundle config set --global gems.example user:secret` writes it), looked for in the project's `.bundle/config` (or `$BUNDLE_APP_CONFIG/config`), then the environment, then the global config (`BUNDLE_CONFIG`, `BUNDLE_USER_CONFIG`, `BUNDLE_USER_HOME/config`, `~/.bundle/config`); `BUNDLE_IGNORE_CONFIG` leaves the files out. User and password are percent-decoded and sent as HTTP Basic credentials with every request to that source, and reqwest drops them on a redirect to another host. The client keeps its URL without them, so no message carries them, and the lockfile's `remote:` never has them (`Source::Rubygems#credless_remotes`). A 401 or 403 is Bundler's message, word for word (`Bad username or password for <host>.`, `Authentication is required for <host>.` with the `BUNDLE_<HOST>` to set, `Access token could not be authenticated`), exit 17.
- **Legacy index.** A source whose `/versions` is a 404 has no compact index, and only then the client reads `specs.4.8.gz` (and `prerelease_specs.4.8.gz`, which may be missing), a gzipped Marshal of `[name, version, platform]` triples, as `Bundler::Fetcher::Index` does; Bundler's dependency API, retired by rubygems.org, is not tried. Each build's dependencies and Ruby and RubyGems requirements come from its `quick/Marshal.4.8/<full name>.gemspec.rz`, read by a Marshal reader of Spinel's own (`crates/spinel-cli/src/marshal.rs`, which never runs a class's `_load`), cached under `quick/` and written into `info/<gem>` as `/info` lines with no checksum, so the resolver and the installer read one shape. A gem with no checksum is stored under the SHA-256 of the `.gem` that arrived, and that fills its `CHECKSUMS` line, as Bundler's lockfile after `bundle install` has it. Not yet: Bundler fetches a build's gemspec only when the resolver reaches it, Spinel every build of each gem reached, which is fine for a private server's handful.

`spinel index [--source URL] [--names] [gem...]` (hidden) runs the client and prints one line per file; `crates/spinel-cli/tests/compact_index.rs` drives it against a local server.

### 3. Resolver

Resolution is PubGrub, as Bundler's is: `crates/spinel-cli/src/resolver/solver/` ports pubgrub-ruby 0.5.0 as Bundler 4.0.20 vendors it (`bundler/vendor/pub_grub`), file for file, so what a resolution derives, and so what it relaxes on a retry and how it explains a conflict, are Bundler's by construction (#816). Spinel supplies:

- **Version type**: `Gem::Version` semantics ported to Rust (segments, prerelease ordering, `~>` pessimistic operator), in `crates/spinel-cli/src/gem_version.rs`, with RubyGems' own `test_gem_version.rb` table and the `~>` cases of `test_gem_requirement.rb` beside it. `spinel run`'s language-version check (cli.md) compares versions with it. `Gem::Requirement`, which reads a Gemfile's and an `/info` line's requirements, is `crates/spinel-cli/src/gem_requirement.rs`.
- **Dependency provider**: `crates/spinel-cli/src/resolver.rs` reads `/info` lines as RubyGems' `GemParser` does (`version[-platform] dep:req&req,...|checksum:...,ruby:...,rubygems:...`), each requirement split on `&` with Ruby's `split`, so an empty one (`rubygems:`, which rubygems.org serves for `archive-tar-minitar` 0.5.1) is no requirement, `>= 0`, as Bundler reads it; filters by platform (`ruby`, `x86_64-linux`, `arm64-darwin-24`, ... using RubyGems' platform matching rules, `Gem::Platform` ported to Rust in `crates/spinel-cli/src/gem_platform.rs` with RubyGems' own `test_gem_platform.rb` beside it) and by `required_ruby_version`, and is modelled on `Bundler::Resolver` so that it chooses what Bundler 4 chooses:
  - **Candidates.** A version is up to two candidates, its `ruby` build (priority -1) and its builds for the resolution platforms (priority 1), ordered by version and then priority, so `= 1.0` covers both and `> 1.0` neither (`requirement_to_range`; `~> 1.4` ends before `2.A`). For each platform the builds `Gem::Platform` installs there are narrowed to the best match (`sort_and_filter_best_platform_match`); a platform build with the ruby build's dependencies joins the ruby candidate, and a platform candidate equal to the ruby one is dropped. A Gemfile gem needs a build for every resolution platform the dependency applies on (its `platforms:`, through Bundler's platform map), any other gem one for some platform. Builds that depend on themselves impossibly are dropped.
  - **Ruby and RubyGems.** `required_ruby_version` and `required_rubygems_version` are dependencies on two meta packages, `Ruby\0` and `RubyGems\0`, each with one version, the one resolved for (Spinel's `RUBY_VERSION` and the RubyGems it ships, unless told otherwise), which the root depends on exactly. So a Ruby requirement rules a version out the way any conflict does, and the explanation says `current Ruby version is = 2.6.10`.
  - **Prereleases** are left out of a gem's candidates unless its Gemfile requirement names one or it has a single build. A Gemfile gem with no candidate otherwise takes them, last; a resolution that fails through a gem whose prereleases were left out is retried with them, as Bundler's `solve_versions` retries: `find_names_to_relax`, ported line for line, walks the failure's `cause.incompatibility` while it is a conflict, naming the gems with a base requirement to unlock and those whose prereleases were left out but that have some to let them in, and not those only in what an earlier conflict taught; it takes a `NoVersions` cause's extended explanation (the builds for other platforms), which follows the explanation. The solver's tests compare it with what pubgrub-ruby itself prints for range operations, Bundler's candidate ranges and Dart pub's `doc/solver.md` examples, recorded by `tests/fixtures/resolver/solver_oracle.rb` (CRuby 4.0.9) in `solver_oracle.txt`. `crates/spinel-cli/src/resolver/source.rs` ports Bundler's source side over the candidates: `Resolver#incompatibilities_for`, which states each dependency for the whole run of versions sharing it, open at the first and last version, `no_versions_incompatibility_for` with Bundler's wording, `parse_dependency`, `versions_for`, and `Resolver::Strategy` with `GemVersionPromoter`'s order. Measured against Bundler 4.0.20 with `relax_compare.py`: every case of 400 random small indexes with prereleases (seed 1) and of 1000 each with seeds 816, 4242, 9001 and 20261120 ends as Bundler's does, resolving to the same gems or failing, and every try relaxes the gems Bundler's relaxes. The fifteen cases in `tests/fixtures/resolver/oracle/` are tested as resolving as Bundler does: the three hand-written ones (`needs_pre`, `case1`, `case2`), and twelve random ones on which the `pubgrub` crate Spinel resolved with before #816 relaxed gems Bundler does not (`case0138`, `seed816-*`, `seed4242-*`). On each, the resolver logs what Bundler logs with `DEBUG_RESOLVER` on every try, line for line (`oracle/<case>/resolution.log`), and relaxes what Bundler relaxes between them (`oracle/<case>/relax.log`).
  - **Order.** The next gem decided is the one with at most one candidate left, then the one with the fewest candidates above its range, then the one found first, a version's dependencies being found last first, as pubgrub-ruby's propagation finds them (`Strategy#next_term_to_try_from`); its candidate is the newest, releases before prereleases unless the Gemfile asked for prereleases, a platform build before the ruby build (`GemVersionPromoter#sort_versions`).
  - **Index.** Before resolving, `/info` is brought up to date for every gem the Gemfile's gems reach through any version's dependencies, round by round, as Bundler fetches them; a gem `/versions` does not list has no builds.
- **Conflict explanations**: `crates/spinel-cli/src/resolver/report.rs` ports pubgrub-ruby's `FailureWriter` line for line over the port's own incompatibilities (`resolver/solver/`), counting and numbering a derivation reached twice as `FailureWriter`'s hashes do, by equal cause and terms. Each incompatibility is written by its `to_s`, with Bundler's wording where Bundler gives one (`Could not find compatible versions`, `Gemfile depends on ...`, `current Ruby version is ...`, `... could not be found in rubygems repository ... for any resolution platforms (...)`), and the extended explanation, the matching builds, after it. Every failure of the random indexes below is explained as Bundler 4.0.20 explains it, word for word but for Bundler's `or installed locally`: 110 of seed 1's 400 cases, 273 of seed 816's 1000 and 279 of seed 4242's 1000, and the seven hand cases in `tests/fixtures/resolver/oracle/` Bundler fails on (`oracle/<case>/bundler.txt`). A Gemfile gem no candidate satisfies fails before resolving with Bundler's `Could not find gem 'rack (>= 99)' in ...` and the builds the source has.
- **Locked preferences** (#79): when `Gemfile.lock` exists and the user did not ask to update, the lockfile holds the resolution as Bundler 4's `Definition` holds it, in `crates/spinel-cli/src/locked.rs`. Bundler does not make a locked version the only candidate; what keeps `bundle install` stable is this:
  - **Nothing changed, nothing resolved.** When the Gemfile asks for nothing the lockfile does not hold, the lockfile's specs are the resolution and the index is never read (`no_resolve_needed?`). A gem taken out of the Gemfile takes with it what only it needed (`SpecSet#for` of the rest); a requirement changed to one the locked version still meets is not a change. So an unchanged Gemfile writes its lockfile back byte for byte. And as `write_lock` leaves one (`lockfiles_equal?` with `preserve_unknown_sections`, no update asked for): unless a major version of Bundler is crossed, a lockfile that differs from what its own `BUNDLED WITH` Bundler would write only in `RUBY VERSION`, `BUNDLED WITH`, sections introduced after that Bundler or sections Bundler does not know is left as it was, so a lockfile from Bundler 4.0.10, its `bundler (4.0.10)` checksum line with it, comes back byte for byte too.
  - **What changes.** A Gemfile gem new to the lockfile's `DEPENDENCIES`, or whose locked version its requirement no longer meets (that gem is unlocked); the local platform when no locked platform runs here (a `ruby` or a less specific one does); a locked spec whose dependencies the lockfile does not meet (dropped); a `CHECKSUMS` line missing or empty; a source other than the lockfile's; and a `ruby` directive come, gone, or no longer met by the locked `RUBY VERSION`.
  - **Resolving with the lockfile.** Every locked gem but the Gemfile's changed ones gets a floor, `>= locked version` (`additional_base_requirements_to_prevent_downgrades`), and its locked version is tried first (`GemVersionPromoter#post_sort`), so a gem moves only up, and only when the rest needs it to. The locked specs a Gemfile dependency they still meet reaches, through no unlocked gem (`converge_specs`), are resolved from the lockfile itself, its dependencies and its builds before the index's on each locked platform (`@base`, `prefer_locked`); one such that the Gemfile names for the first time is pinned to its locked version exactly. A locked prerelease lets that gem's prereleases in. On a conflict, the gems along its first causes that have such a requirement lose it, an exact pin a gem the Gemfile does not name has first, then any exact pin (each becoming a floor), then a floor, and the resolution is tried again (`find_names_to_relax`, `Base#unlock_names`), with the prerelease retry above alongside. So a gem a new requirement pushes down can take others further down than a fresh resolution would: adding `rack "< 3"` to a lockfile with Sinatra 4 and rackup 2 settles on Sinatra 1.0 and rackup 1.0.1, as Bundler does, since the floors on rack-protection and rackup's newer versions still stand.
  - **The lockfile written.** The result keeps each locked build of a version chosen (`specs_with_additional_variants_from`), then `SpecSet#for` of the Gemfile on the lockfile's platforms and `ruby`; no extra platforms are added. `CHECKSUMS` is written when the lockfile had it, each line the lockfile's, or the index's SHA-256 for a spec it had none for; `RUBY VERSION` is the locked one while the directive allows it.
  - **Updating** (#87): `bundle update` and `bundle lock --update` pass `Definition` what to unlock, and so does `spinel update` (section 11). With gems named, those gems and every locked gem they reach (`SpecSet#for` of them, `@gems_to_unlock`) are unlocked: they leave the base, their locked versions are no longer tried first and their locked builds no longer preferred; and each named gem is pinned to the version a resolution with every gem unlocked and no base gives it (`additional_base_requirements_to_force_updates`), which a conflict loosens to a floor as any pin. With none, every gem is unlocked and the base is empty (`@unlocking_all`). Either way the `>= locked version` floors stay, so nothing goes down unless a conflict takes a floor off, and the lockfile is written as resolved, never left as it was. `spinel resolve --locked --update[=GEM,...]` runs it.
  - Not yet: `bundle update`'s `--conservative`, `--patch`, `--minor`, `--major`, `--strict`, `--pre` and `--group`, a platform added that the result has no builds for (Bundler's `raise_incomplete!`), and a locked platform the lockfile's own specs cannot install on (`remove_invalid_platforms!`).

A dependency on `bundler` (Rails has one) resolves to one version only, the Bundler the lockfile is written for (`lockfile::BUNDLER_VERSION`), as Bundler's `Source::Metadata` offers only the Bundler running: no `/info/bundler` is read, and no resolution lists it, since `SpecSet#for` never materializes it.

A gem a git or path source has comes only from that source: its gemspec's spec stands in for the index's builds of the name, and the index is read for what it depends on (section 12). A rubygems source scoped to some gems (`source "..." do`, or `gem ..., source:`, #89) provides them as `SourceMap#all_requirements` assigns them: the gems pinned to it, and every gem its index reaches from those that the Gemfile does not name itself; a gem two scoped sources would provide is Bundler's `The gem '<name>' was found in multiple relevant sources.`, exit 19. The rest come from the global source. Each rubygems source is a `GEM` section of its own, sorted by `rubygems repository <remote>` after the git and path sources, its pinned gems `!` in `DEPENDENCIES`, and its gems fetched from it. Not yet: a conflict's explanation names the global source for every gem, and a scoped source with no compact index is read as if it had one, where Bundler warns and aggregates.

`spinel resolve [--platform P]... [--lockfile] [--locked Gemfile.lock [--update[=GEM,...]]] [--ruby-version V] [--rubygems-version V] <deps.json | ->` (hidden) resolves the JSON `shims/gemfile_eval.rb` prints against its source's index for the platforms given (the first is taken as the local one) and prints one line per build as a lockfile's `specs:` lists them, or with `--lockfile` the whole new `Gemfile.lock` (section 4), or the explanation on stderr, exit 1. With `--locked`, the lockfile holds the resolution as above: its `PLATFORMS` are the resolution platforms, the first `--platform` the local one and any other added as `bundle lock --add-platform` adds it; `--update` updates as `bundle lock --update` does, every gem or the gems named. With `DEBUG_RESOLVER` set it logs its facts and decisions on stderr as Bundler does, and with `SPINEL_DEBUG_RELAX` what each failed try relaxes. `crates/spinel-cli/tests/resolver.rs` runs it on the Gemfiles in `tests/fixtures/resolver/cases/` against `tests/fixtures/resolver/index/`, a snapshot of rubygems.org's `/info` for Sinatra, rackup, WEBrick and json and everything their versions depend on (`snapshot.sh` takes it; `index/SOURCE` dates it), served on 127.0.0.1, and checks each against what Bundler 4.0.20 resolved for the same Gemfile, snapshot, platforms and Ruby (`bundler.sh`, which records Bundler's `Gemfile.lock` or explanation): Sinatra's set, a Ruby too old for Sinatra 4, backtracking, `java` builds, prereleases asked for and not, and five failures, four of them explained word for word as Bundler explains them, after relaxing what Bundler relaxes, and one differing by Bundler's `or installed locally`. Four opt-in tools, never run by CI, check the resolver against Bundler beyond the snapshot: `bundle_case.sh <dir>` runs Bundler through `bundler_oracle.rb` on a synthetic index (`info/<gem>` and `Gemfile.gems`), as for the cases in `oracle/` whose results the unit tests assert, and `differential.py --spinel <binary> --cases N --seed S --out <scratch>` compares `spinel resolve` with Bundler on random small indexes, keeping each case where they differ: where both fail, in their explanations, word for word from `Could not find` with the served URL and Bundler's `or installed locally` set aside (`explained-diff`). With `--locked [--steps N]` it locks each case with Bundler, edits the Gemfile (left alone, a gem added or taken out, a requirement changed) N times in a row, and compares each lockfile Bundler writes with the previous one in place to what `spinel resolve --locked` writes, byte for byte; a difference that remains with no lockfile is tagged `-unlocked-too`; `--updates` makes some of the edits updates, `bundle lock --update` of every gem or of one the lockfile locks, the Gemfile left as it was. Measured: seeds 1 and 2 (400 cases, one edit) 519 lockfiles identical, 57 both failed, none different; with `--steps 3 --updates`, seed 1 (400 cases) 224 identical and 66 both failed, seeds 816 and 4242 (1000 each) 590 and 584 identical and 137 each both failed, none different (each case's first lock by Bundler failing in the rest). The third, `decision_log.py --spinel <binary> [--all] <dir>...` runs both with `DEBUG_RESOLVER` on such case directories and compares every try's decisions (`attempting`, `selected`, `derived:`), or with `--all` every line pubgrub-ruby logs, of `spinel resolve` with Bundler's; `--write` records Bundler's as `resolution.log`, and what each of its tries' `find_names_to_relax` returned as `relax.log`. ### 4. Lockfile

`crates/spinel-cli/src/lockfile.rs` reads a lockfile as Bundler 4's `LockfileParser` reads it and writes one as its `LockfileGenerator` writes it: `GEM` (its `remote:`s), `GIT` (`remote`, `revision`, `ref`, `branch`, `tag`, `submodules`, a glob that is not the default), `PATH` and `PLUGIN SOURCE` sections, each with its `specs:`, then `PLATFORMS`, `DEPENDENCIES` (`!` on a dependency pinned to a source of its own), `CHECKSUMS` (Bundler ≥ 2.5; written only when the lockfile has it, a line for every locked spec), `RUBY VERSION` and `BUNDLED WITH`. Lines are matched by a port of `NAME_VERSION`, and written in the generator's order, not the order read: specs by `full_name`, a spec's dependencies and the `DEPENDENCIES` by `to_s`, requirements within a line sorted and reversed (`rack (>= 3.0.0, < 4)`), platforms and checksum lines sorted. Git and path sources are read and written back whole; a resolution writes them as section 12 says. A section Bundler does not know is dropped, as Bundler drops it when it writes; a merge conflict, a version that does not parse, and two digests of one algorithm for one gem fail with Bundler's messages.

A resolution held by a lockfile (#79) is written as the resolver section describes, with the lockfile's platforms, checksums and `RUBY VERSION`. A new lockfile is written from a resolution as `bundle lock` writes one where there is none: the specs, the Gemfile's dependencies, a `CHECKSUMS` line per spec from its `/info` `checksum:` (Bundler 4 writes `CHECKSUMS` into every new lockfile), `RUBY VERSION` when the Gemfile has a `ruby` directive (`ruby <version>`, the Ruby resolved for), and `BUNDLED WITH` 4.0.20, the one constant `lockfile::BUNDLER_VERSION`: the Bundler whose lockfiles the fixtures are, byte for byte, and whose resolver the resolver is measured against. `PLATFORMS` are shaped as `Definition#start_resolution` shapes them when the local platform's generic one is `ruby`: `SpecSet#add_extra_platforms!` adds each platform some locked gem has a build for whose generic platform is `ruby` and on which every locked gem has a build, valid with what is already locked, that installs there (`SpecSet#complete_platform`, which adds those builds); `ruby` comes in when nothing needs a native build, and does not when, say, nokogiri's ruby build needs `mini_portile2` and its native builds do not. When a more specific name for the local platform came in (`x86_64-linux-gnu` for `x86_64-linux`), the local one is dropped. The specs are then `SpecSet#for` of the Gemfile's dependencies on those platforms and `ruby`. `bundle lock` with `lockfile_checksums` off, which leaves `CHECKSUMS` out, is not followed: Spinel reads no Bundler settings but a source's credentials.

`spinel lockfile <Gemfile.lock | ->` (hidden) reads a lockfile and prints it back as Bundler would write it. `crates/spinel-cli/tests/lockfile.rs` checks both directions against lockfiles Bundler 4.0.20 wrote: every one in the fixtures (the five under `tests/fixtures/lockfile/cases/`, the six resolved resolver cases and the Sinatra app's) reads back and writes out byte for byte, and for each Gemfile among them with one rubygems source, `spinel resolve --lockfile` writes the lockfile Bundler wrote, byte for byte: `rails new`'s Gemfile (118 gems, seven platforms Bundler added, `x86_64-linux` given up), one with ten platforms, a `ruby` directive, and the resolver's Sinatra, Ruby 2.6, backtracking, `java` and prerelease cases. The `lockfile` cases are locked by `tests/fixtures/lockfile/bundler.sh` against `tests/fixtures/lockfile/index/`, rubygems.org's `/info` for the Rails tree and a few more roots, trimmed to each gem's three highest versions and the highest one meeting each requirement a kept build puts on it (`snapshot.rb` takes it); the `sources` case adds GIT (a branch, and a tag with a glob), PATH and a second, scoped GEM source, from git repositories `bundler.sh` commits with a fixed author and date. `tests/fixtures/lockfile/install_check.sh` (opt-in: it needs Ruby) runs real `bundle install` on what Spinel writes for the `rails`, `multi_platform` and `ruby_version` cases, against a copy of the snapshot whose checksums are those of stand-in `.gem`s `dummy_gems.rb` builds for every locked spec, once frozen and once not, and checks the lockfile comes out byte for byte as Spinel wrote it.

The lockfile never mentions Spinel. `PLATFORMS` lists `ruby` and the usual RubyGems platforms; Spinel-native extension substitutions (section 6) are recorded in `.spinel/substitutions.json`, not in the lock. That is what keeps the lock acceptable to Bundler.

### 5. Global store

`<home>/store/gems/<name>-<version>-<platform>-<sha256>/` holds one gem, keyed by its content: `<sha256>` is the SHA-256 of its `.gem` in hex, as the index's `/info` line (later the lockfile's `CHECKSUMS`) lists it, and `<platform>` is `ruby` for a gem with none. In it, `gem/` is `data.tar.gz` unpacked and `metadata` is the gemspec as YAML, from `metadata.gz`. A gem is fetched once for every project: one already stored with that checksum costs no request, and two sources serving different bytes under one name never share an entry. Per project, `.spinel/gem_home/gems/<full name>` is a **symlink** to the entry's `gem/`, `specifications/<full name>.gemspec` is a real file (RubyGems wants to read it), `bin/` gets generated stubs; "GEM_HOME" below has the rules.

// ponytail: symlinks. Hardlink-per-file (pnpm style) if a gem ever needs to write into its own directory; none of the top 1000 do.

The store is `crates/spinel-cli/src/gem_store.rs`:

- **Fetch.** `GET <source>/gems/<full name>.gem` through the index client's HTTP client, under its limit of 32 requests in flight, streamed to `store/tmp/` and hashed as it arrives. A `.gem` whose SHA-256 is not the listed one is refused, and a gem the index lists with no checksum is refused too, since the store is keyed by it.
- **Unpack**, as `Gem::Package` verifies and extracts one: a part named twice, a missing `metadata.gz` or `data.tar.gz`, or a part whose SHA256 or SHA512 differs from `checksums.yaml.gz` refuses the gem (SHA1, which RubyGems 2 also wrote, is not checked; those gems list SHA512 too). Signatures are not checked, as `gem install` does not check them without a trust policy. Every entry of `data.tar.gz` must name a path inside the gem's directory; directories, files (with their permission bits, never setuid, setgid or sticky) and symlinks are written, and any other kind of entry is passed over. Symlinks are made last, so nothing is written through one, and each must point inside the gem by its spelling, as RubyGems requires, and also where it physically leads once made, which catches `a/b/c/up -> ../..` followed by `a/b/c/up/x -> ../../..`. A symlink may not replace an existing directory or symlink, so no symlink checked earlier can be redirected through one made later; every symlink is checked again once all are made. A dangling one is left out with RubyGems' warning.
- **Atomicity.** The entry is built in `store/tmp/<pid>-<n>/` and renamed into `store/gems/` whole, so an entry that exists is complete; a cut connection, a refused archive or a killed process leaves only staging files, which the next run removes once the process that made them has exited. Two `spinel`s storing one gem at once both fetch it, and the second rename finds the first's entry and keeps it. Nothing is fsynced (a `ponytail:` in `gem_store.rs`).

Fetch and unpack run in parallel (`tokio`: downloads on the runtime, unpacking on blocking threads, at most one per CPU), so a cold install is network-bound, not CPU-bound. A warm install (everything in the store) is link creation only: `spinel install` takes each checksum from the lockfile's `CHECKSUMS`, so with nothing to resolve it makes no request at all. `bench/install.sh` times both for a Rails app's lockfile, beside `curl` fetching the same files and `bundle install`, and its numbers are the table in `bench/README.md` (validation target 5).

`spinel fetch [--source URL] <name@version[-platform]>...` (hidden) brings the index up to date, reads each gem's checksum from its `/info` line, and fetches into the store, printing one line per gem; `crates/spinel-cli/tests/gem_store.rs` drives it against a local server with real `.gem`s that `tests/fixtures/gem_store/build.sh` builds with `gem build`.

#### GEM_HOME

`crates/spinel-cli/src/gem_home.rs` links stored gems into a project's `.spinel/gem_home/`, laid out as `gem install --install-dir` lays one out:

- **Directories.** `Gem::REPOSITORY_SUBDIRECTORIES` (`build_info`, `cache`, `doc`, `extensions`, `gems`, `plugins`, `specifications`) and `bin`, as `gem install` makes them.
- **`gems/<full name>`** is a symlink to the store entry's `gem/`, the name being the gemspec's `full_name` (`name-version`, and `-platform` unless it is `ruby`). The gemspec must name the gem asked for. Each executable gains `0o111`, as `Gem::Installer#generate_bin` leaves it; the file is the store's, and the change is the same for every project.
- **`specifications/<full name>.gemspec`** is what `Gem::Installer#write_spec` writes: `installed_by_version` set to the RubyGems Spinel ships (4.0.16, in `stdlib/`), then `to_ruby_for_cache`. Loading the stored YAML needs Psych, a C extension Spinel did not have when this was written (it is a built-in since #108, and this port stays), and a warm install should not boot a VM per gem, so both halves are ported to Rust in `crates/spinel-cli/src/gem_spec.rs`: Psych's load for what a gemspec holds (the `Gem::` classes `Gem::SafeYAML` permits, `ScalarScanner#tokenize` for plain scalars, anchors and aliases, `!binary`), `from_yaml`'s defaults, and `to_ruby` through the same getters and `ruby_code`, `String#dump` included. Before it is written, `Gem::Installer#verify_spec`'s checks refuse what would put code into that text or a stub outside the GEM_HOME: a line break in a require path, extension or platform, a `specification_version` that is not digits, a dependency name with `<`, `>` or a line break, an executable that is not a plain file name, a `bindir` outside the gem; and only `:runtime` and `:development` load as Symbols, as `Gem::SafeYAML` permits. A gemspec whose YAML nests deeper than 256 or builds more than 1 GiB with its aliases expanded is refused where Psych would load it (a `ponytail:` in `gem_spec.rs`). Its test compares the output with CRuby running that RubyGems on fixtures written to reach the format's corners and on real gems (`tests/fixtures/gem_spec/build.sh`), byte for byte; `SPINEL_GEMSPEC_CORPUS` points the same test at a larger set made the same way.
- **`bin/<executable>`** is `Gem::Installer#app_script_text` with `--env-shebang`, whose first line on Spinel is `#!/usr/bin/env spinel` (cli.md). Spinel counts a `#!` line naming `spinel` as a Ruby one, as CRuby counts one naming its engine, so the stub runs as a program. An executable the gem does not have gets no stub, as in RubyGems; two gems with one executable is a warning, and the later wins.
- **Not done.** `cache/` stays empty: the store does not keep the `.gem` once unpacked, and nothing `Bundler.setup` or `bundle exec` reads needs it. Extensions are not built: a built-in gem is not fetched at all (section 6, step 1, #83), and a gem that has some and no built-in is linked with a warning, and RubyGems will not activate it, unless a Spinel-native substitute stands in for it (section 6, step 2, #112). `plugins/` gets no `rubygems_plugin.rb` stubs.
- **Idempotent.** What is already right is not written again, so linking the same gems twice writes nothing. A gem a previous link made and the list no longer names is removed: its symlink (only a symlink counts as one a link made, as `gem install` makes directories), its gemspec, and its bin stubs while they are still the ones a link writes and no gem the GEM_HOME still has owns them. Nothing else in the GEM_HOME is touched, so a gem `gem install`ed into it stays. Every gemspec is read before anything is written, so a gem RubyGems would refuse leaves the GEM_HOME as it was; each file and symlink is made beside its place and renamed into it.

`spinel fetch --gem-home DIR ...` links what it fetched, only when every gem was fetched, and prints `gem home: <dir>` and then `<full name>: linked` (something written), `current` (nothing to write) or `removed`. `crates/spinel-cli/tests/gem_home.rs` drives it against a local server with the store's fixtures and checks the GEM_HOME against the one RubyGems makes of the same `.gem`s (`tests/fixtures/gem_home/build.sh`), then reads it on Spinel through RubyGems (`require`, `Gem::Specification`, a bin stub run by its `#!`), `Bundler.setup` and `bundle exec`, the latter with the `libexec/bundle` Spinel extracts beside its stdlib (#71, cli.md, "Bundler running on Spinel"); nothing of the GEM_HOME is adjusted for it.

### 6. Native extensions

There is no `extconf.rb`, no mkmf, and no C compiler in the loop. See engine.md, "Native extensions and FFI". The resolver works on the ordinary gem set, exactly as Bundler would lock it; substitution happens at install time and is invisible to the lockfile.

Per locked gem, in order:

1. **Built-in gem.** Spinel ships pinned versions of the default gems whose C parts are Spinel primitives (engine.md, "Built-in gems"). If the lock pins one of these, Spinel uses its built-in copy and skips the gem's `ext/`. A different patch version is silent; a different minor version warns; a different major version fails, because the gem's Ruby half may expect a different primitive surface. The rules are in `crates/spinel-cli/src/builtin_gem.rs` (#83):
   - **Which gems.** `bigdecimal` 4.0.1, `date` 3.5.1, `digest` 3.2.1, `etc` 1.4.6, `fcntl` 1.3.0, `fiddle` 1.1.8, `io-console` 0.8.2, `json` 2.18.0, `openssl` 4.0.2, `psych` 5.3.1, `stringio` 3.2.0, `strscan` 3.1.6 and `zlib` 3.2.3, each at the version its Ruby source claims (an integration test requires each one and checks its runtime constant). `openssl` is listed from its first phase (#106: digests, HMAC, random bytes; TLS and `net/https` since #107), since the gem itself cannot stand in: its `openssl.rb` requires `openssl.so`, a CRuby extension Spinel never builds. `bigdecimal` joined it with #109, and `racc` joins it when it becomes a built-in; `monitor` names no gem version yet. A lock pinning a gem not on the list installs the gem itself.
   - **Skew.** Judged between the locked version and the built-in's: the first segment is the major version, the second the minor, a missing one `0`. A minor apart is one warning naming both versions; a major apart fails the install, naming every such gem and the requirement that keeps it to the built-in's version, before anything is written.
   - **Install.** The gem is neither fetched nor unpacked, so nothing of its `ext/` is built or written. The GEM_HOME gets the locked identity: `specifications/json-2.18.0.gemspec`, with the locked name, version and platform and the lockfile's runtime dependencies, no extensions and no executables, and `gems/json-2.18.0` a symlink to `~/.spinel/builtin/json-2.18.0/`, whose `lib/` is empty. `Bundler.setup` therefore activates the `json` the lock names, and `require "json"` loads the built-in where it always does: an embedded `lib/<name>.rb` before the load path, the standard library's on it. `.spinel/substitutions.json` records `json 2.18.0 ruby → built-in 2.18.0`, and the lock keeps `json (2.18.0)`. `spinel x` does not substitute yet.
2. **Spinel-native gem.** For gems like `pg`, `sqlite3`, `nio4r` and `puma`, a substitute is published to rubygems.org under its own name, `<gem>-spinel` (`pg-spinel`), with ordinary RubyGems platforms. These gems contain a `.spinel` extension built with `spinel-ext`, or pure Ruby on `Spinel::FFI`, and present the upstream gem's Ruby API (`require "pg"`). On any other Ruby, requiring one raises a `LoadError` that names Spinel. The rules are in `crates/spinel-cli/src/gem_substitute.rs`:
   - **Which gems.** Only gems on Spinel's built-in list of substitutes (the "Spinel-native gems list" of step 4, `SUBSTITUTED` in `gem_substitute.rs`) are substituted. A gem whose name happens to end in `-spinel` is never trusted: anyone can push one, and rubygems.org already has gems such as `bundler-spinel` that are not Spinel's. A name joins the list once the project owns it on rubygems.org; it owns none yet, so the list is empty (a `ponytail:`). `SPINEL_SUBSTITUTES`, a comma-separated list of gem names, adds to it for one run, for a substitute's author trying one from their own source before it is listed and for the tests; it trusts whatever `<gem>-spinel` that gem's source serves. The substitute is read from the source the locked gem comes from, the scoped one when a `source` block or `source:` pins it; its `/info` is brought up to date on every install that locks a listed gem, so such an install asks the source even when nothing changed (a `ponytail:` in `install.rs`).
   - **Version.** A substitute's version is the locked upstream version string, a `.`, and a revision, which is a positive integer with no leading zero. `pg 1.5.0` is substituted by `pg-spinel 1.5.0.1`, `1.5.0.2`, and so on, and the highest revision wins. The match is on the lock's string, as RubyGems normalizes it (`2.0.0-rc1` is `2.0.0.pre.rc1`), so `pg-spinel 1.5.0.1` substitutes only `pg 1.5.0`, never `1.5` and never `1.5.0.1`. No `Gem::Requirement` expresses this, so the rule is a function. A substitute never moves the locked version: if no substitute exists for exactly that version, the gem falls through to step 4.
   - **Platform.** Builds use the standard platform for each system Spinel runs on, and Linux names its libc, because a `.spinel` extension links one: `x86_64-linux-gnu`, `x86_64-linux-musl`, `aarch64-linux-gnu`, `aarch64-linux-musl`, `arm64-darwin`, `x86_64-darwin`, or `ruby` for a pure-Ruby substitute. Each of Spinel's `RUBY_PLATFORM`s accepts exactly one of them. A bare `x86_64-linux` would also be accepted on musl. Among the builds of the newest revision that `Gem.platforms` accepts, Spinel takes the one `sort_best_platform_match` ranks first, as RubyGems would.
   - **Install** (#112). The upstream `.gem` is never fetched; the substitute's is, into the store like any gem, checked against the SHA-256 its `/info` line lists. The GEM_HOME gets the locked identity: `specifications/pg-1.5.0.gemspec`, with the locked name, version and platform and the lockfile's runtime dependencies (upstream's), no extensions, and the substitute's require paths, `bindir` and executables; and `gems/pg-1.5.0` a symlink to the substitute's files in the store. Nothing in the GEM_HOME is named `pg-spinel`. `Bundler.setup` running on Spinel therefore finds the `pg 1.5.0` the lock names. A substitute may depend only on gems upstream depends on, at versions the lock holds: one that needs a runtime dependency upstream does not have, or a version of one that the lock's version for that gem (over all the lock's specs, not only this platform's) does not satisfy, fails the install, because the lock would not contain what it needs: `pg-spinel-1.5.0.1 cannot stand in for pg 1.5.0: it depends on ffi (>= 0), which pg does not, so Gemfile.lock locks nothing for it; it depends on bigdecimal (>= 3), which Gemfile.lock locks at 2.0.0`, every such dependency named with its requirement, before anything is fetched or written. A dependency on `bundler` is never refused: as in `SpecSet#valid?`, it is the Bundler the lockfile is written for, never a locked spec. `.spinel/substitutions.json` records `pg 1.5.0 ruby → pg-spinel 1.5.0.1 arm64-darwin`, and the lock keeps `pg (1.5.0)`. The output names the locked gem, `+ pg 1.5.0`, as for any other, its platform too when the lock locks a build of one (`+ sqlite3 2.10.2-x86_64-linux-gnu`).
   - **`.spinel/substitutions.json`** is `{"substitutions": [...]}`, one object per locked gem something else stands in for, sorted by its full name, written on every install so it says what that install did. Each has the locked `name`, `version` and `platform` and a `kind`: `"builtin"` with the `substitute_version` Spinel ships (step 1), or `"native"` with the `substitute`'s name, `substitute_version` and `substitute_platform`:

     ```json
     {
       "substitutions": [
         {
           "kind": "native",
           "name": "pg",
           "platform": "ruby",
           "substitute": "pg-spinel",
           "substitute_platform": "arm64-darwin",
           "substitute_version": "1.5.0.1",
           "version": "1.5.0"
         }
       ]
     }
     ```
   - **Stock Bundler** resolves by name: it reads `/info/pg` and never `/info/pg-spinel`, so it never installs a substitute in place of the gem. This was verified against RubyGems / Bundler 4.0.20 for `bundle lock` on ten platforms, `bundle install`, `bundle update`, `gem install` on four platforms, and a requirement only `pg-spinel` satisfies; each one left `pg-spinel` out. A Gemfile that names `pg-spinel` itself, `pg` being listed, gets it as an ordinary gem with no substitution, and Spinel warns: `the Gemfile names pg-spinel, Spinel's substitute for pg: it is installed as an ordinary gem, not in pg's place; `gem "pg"` gets it in pg's place`.

   `crates/spinel-cli/tests/substitute.rs` checks it against `tests/fixtures/substitute/` (`build.rb`, opt-in, builds its `.gem`s and compact index with RubyGems and has Bundler 4.0.20 lock `app/Gemfile`), served on 127.0.0.1, with `SPINEL_SUBSTITUTES=widget`: `widget 1.0.0` installed as `widget-spinel 1.0.0.2` (the newest revision of that version, among others for `java` and for `1.0.1`), `widget` itself never fetched, `Bundler.setup` activating `widget-1.0.0` with the substitute's files, and Bundler's lockfile, `ruby` entry and all, byte for byte the same after the install and after a fresh resolution with none; off the list, `widget` itself; a substitute that depends on a gem upstream does not; and a Gemfile naming `widget-spinel`. With `SPINEL_CRUBY_BUNDLER` set and CRuby 4.0's `bundle` on `PATH` (CI's Linux leg), stock `bundle install` on the same project installs `widget` itself, never asks for `/info/widget-spinel`, and leaves the lockfile byte for byte as it was.

   **`sqlite3-spinel`** (#113) is the first: `gems/sqlite3-spinel/`, version `2.10.2.1`, standing in for `sqlite3 2.10.2`. Its `lib/` is upstream's, verbatim (`vendor.sh --check`, in CI's stdlib drift job, compares it with the packaged gem), but for `lib/sqlite3/sqlite3_native.rb`, which upstream's `lib/sqlite3.rb` requires where CRuby loads `sqlite3_native.so`: the C extension's `Database`, `Statement`, constants and exceptions in Ruby, check for check and message for message, over `SQLite3::Spinel`, a `.spinel` extension (`ext/sqlite3_spinel`, a workspace member) whose methods are SQLite's C calls one for one. SQLite comes as upstream's precompiled gems have it: the amalgamation of the release sqlite3 2.10.2 bundles, 3.54.1, compiled in, here by libsqlite3-sys 0.40.0's `bundled`, its compile options brought to upstream's by `.cargo/config.toml` (foreign keys off by default, `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`, the dbpage and dbstat tables). What would call into Ruby from inside SQLite raises `NotImplementedError`, since `spinel-ext` cannot call a method yet: `create_function`, `create_aggregate`, `collation`, `trace`, a busy handler block, an authorizer and `statement_timeout=`; `SQLite3::Backup`, `serialize` and `deserialize` are not there (a `ponytail:` in `sqlite3_native.rb`). `build.rb`, run by `spinel` or `ruby`, builds the extension with cargo and packages `sqlite3-spinel-2.10.2.1-<platform>.gem` with RubyGems' `Gem::Package.build`, for the platform above that names the machine. ### 8. `spinel install`

`crates/spinel-cli/src/install.rs` runs the steps above in order and adds nothing of its own:

- **Gemfile.** `shims/gemfile_eval.rb`, embedded in the binary, runs on the VM in a child `spinel`, from the current directory, so it finds `BUNDLE_GEMFILE` or the nearest `gems.rb`/`Gemfile` as Bundler does. The project is the Gemfile's directory, and the lockfile is beside it: `Gemfile.lock`, or `gems.locked` for a `gems.rb`. An error in the Gemfile is the evaluator's, exit 1.
- **Resolution.** With a lockfile, `locked::Definition` holds the resolution to it (section 3, "Locked preferences"): nothing changed, nothing resolved and the index never read; otherwise the index is read and the lockfile `write_lock` leaves is written. With none, a fresh resolution and the lockfile `bundle lock` writes (section 4). A conflict is the resolver's explanation, exit 1.
- **What is installed** is `SpecSet#for` of the lockfile's builds on the local platform, from the Gemfile dependencies `Definition#requested_dependencies` installs: those on this platform whose `install_if` held and whose `env` is set, in any group that is not only `optional: true` ones. Spinel reads no Bundler settings but a source's credentials, so there is no `--without`.
- **Store and GEM_HOME.** Each gem's checksum is its `CHECKSUMS` line, else the index's `/info` line; the store fetches what it does not have (section 5), and every gem is linked into `.spinel/gem_home/` at once, which removes what an earlier install linked and the lockfile no longer names. A gem that fails to fetch or verify fails the install before the GEM_HOME or the lockfile is touched.
- **Then** the GEM_HOME's views for Bundler (`ruby/4.0.0/` and `spinel/4.0.0/`, symlinks to its subdirectories, but for CRuby's `bin/` of CRuby's stubs), `.bundle/config` and the lockfile, each written only when it changed, beside itself and renamed into place; the other settings in `.bundle/config` are kept. The output is one line per gem added (`+ rack 3.2.8`), per gem removed (`- webrick 1.9.2`) and per gem whose one version gave way to another (`~ widget 1.0.0 -> 1.1.0`), sorted by name, and, when no gem changed, the one line `Nothing to change`, or `Updated Gemfile and Gemfile.lock; no gems changed` naming the files the run wrote (`spinel add rack` with rack already locked as a dependency writes both). `spinel add`, `remove` and `update` end in this step, so they print the same summary.
- **`--frozen`** is Bundler's frozen mode (`ensure_equivalent_gemfile_and_lockfile` for an explicit flag): before anything is resolved or written, a Gemfile the lockfile no longer holds (a gem added, taken out or with a requirement its locked version no longer meets, a changed source, a lockfile missing a checksum or a dependency, a `ruby` directive come or gone) is `lockfile_changes_summary`'s message, word for word as Bundler 4.0.20 writes it but for `spinel install` in place of `bundle install`, and exit 16, Bundler's `ProductionError` status; no lockfile is `Frozen mode is set, but there's no lockfile`. Otherwise it installs from the lockfile and never writes it. `crates/spinel-cli/tests/install.rs` checks each message against Bundler's.

`crates/spinel-cli/tests/private_source.rs` installs from gem servers on 127.0.0.1 (`tests/fixtures/private_source/`, built by `snapshot.rb` from the `.gem`s below): a compact index behind HTTP Basic credentials taken from the source's URL, `BUNDLE_127__0__0__1` and `.bundle/config`; one with no compact index, through `specs.4.8.gz`; and a public global source beside a private one scoped to `rackup`. Each lockfile is the one Bundler 4.0.20 wrote for the same Gemfile (`bundler.sh`, opt-in, records it, and Bundler's messages for a credential refused and none given), byte for byte; the credential is in neither the lockfile nor the output, and the public server never sees it.

`crates/spinel-cli/tests/install.rs` runs it against rubygems.org's own files served on 127.0.0.1 (`tests/fixtures/install/`, which `snapshot.sh` takes: `/info/rake`, and the real `.gem`s of the newest rake and of every gem the Sinatra fixture locks, each checked against its checksum): `fixtures/plain` resolved afresh to the lockfile `bundle lock` writes, rake installed and `spinel run -e 'require "rake"'`; a second install that fetches and writes nothing, and a second project that links from the store; a gem taken out of the Gemfile and so out of the GEM_HOME; `--frozen` silent on an unchanged lockfile and failing as Bundler does on each change; and `fixtures/sinatra-lock` installed from its lockfile, which comes back byte for byte, then its `app.rb` serving a request on WEBrick. That last one needs `openssl`: Sinatra names rack-session's cookie store as it loads, and that requires `openssl`, which is Spinel's built-in (#106; until it landed, the test put a stand-in on the load path).

### 9. `spinel add`

`crates/spinel-cli/src/add.rs` is `bundle add` (`CLI::Add`, `Injector#inject`) followed by section 8, and `crates/spinel-cli/src/gemfile_edit.rs` writes the lines:

- **Arguments.** `spinel add GEM[@REQ]... [-g|--group a,b] [--git URL]`. A requirement after `@` is `--version`'s list, comma-separated (`sinatra@~> 4.1, >= 4.1.1`); one that is not `Gem::Requirement::PATTERN` is Bundler's `Invalid gem requirement pattern '...'`, exit 15. `--group default` is no group, as Bundler reads it.
- **What is added.** A gem the Gemfile already lists with the same requirement (`Gem::Requirement#==`) is dropped, whatever its groups, as `@deps -= builder.dependencies` drops it; with none left, it is `spinel install`. The rest are evaluated after the Gemfile under the name `injected gems`, as `bundle add` evaluates them, so a gem listed with another requirement is the evaluator's version of Bundler's error, `Gem already added` and its update prompt included, word for word but that the prompt names `spinel update` (section 11), exit 1. Then they resolve with the lockfile held, and each line is written with the requirement asked for, else `~>` the version resolved: its first two segments, three below 1.0, and any prerelease part (`Injector#conservative_version`; `~> 4.2` for Sinatra 4.2.1).
- **The line.** `gem "name", "req"...` with `group: :dev` or `groups: [:dev, :test]`, then `git: "URL"`, as `build_gem_lines` writes it. It is spliced into the Gemfile's own bytes; nothing else in the file is rewritten, so comments, quoting, spacing and a missing last newline stay. Where `spinel_ast` finds a top-level `group ... do ... end` block whose arguments are exactly the groups given (as Symbols or Strings, in any order), the lines go at the end of that block, before its `end`, indented as its last statement or two spaces in from the `group`, and without the `group:` option. Otherwise they are appended as `Injector#append_to` appends them: a newline, which ends a last line that had none and leaves a blank line otherwise, then the lines; before an `__END__` line rather than after it. A file whose first line ends in `\r\n` gets `\r\n`s.
- **Nothing half-written.** Unlike `bundle add`, which appends the line once the gems resolve and leaves it there when the install that follows fails, nothing is written before the install has fetched and linked everything. The new Gemfile is evaluated before it is written and must list each gem with the requirement and groups asked for; it is written just before the lockfile (to the file a symlink names, with its permissions kept), and put back if the lockfile cannot be. A failed resolution, fetch or link leaves the Gemfile and the lockfile as they were, byte for byte.
- **`--git`** writes `git:` after the requirement, `~>` the version the repository's gemspec has at the revision its default branch is at, as `bundle add --git` writes it, and the git source installs as section 12 says.

`crates/spinel-cli/tests/add.rs` runs it against the resolver's snapshot of rubygems.org's index and the install snapshot's `.gem`s, served on 127.0.0.1, on Gemfiles it writes, and checks every byte of each Gemfile after: `spinel add sinatra` on one with comments, single quotes, odd spacing and no last newline, which `spinel install --frozen` then finds unchanged; requirements given and not; groups into the blocks that name them and, with none, as an option; a gem already listed, with the same requirement and with another; and an unmet requirement, an unknown gem, a gem whose `.gem` cannot be fetched and a `--git` repository that is not there, each leaving the Gemfile, the lockfile and the GEM_HOME as they were. The lines expected are what `bundle add` 4.0.20 wrote for the same Gemfiles and index, but for those a block takes.

### 10. `spinel remove`

`crates/spinel-cli/src/remove.rs` is `bundle remove` (`CLI::Remove`, `Injector#remove`) followed by section 8, and `gemfile_edit::remove` takes the lines out:

### 11. `spinel update`

`crates/spinel-cli/src/update.rs` is `bundle update` (`CLI::Update`) followed by section 8, the resolution `locked::Definition`'s with what to unlock (section 3, "Updating"):

- **Arguments.** `spinel update GEM...` updates the gems named; `spinel update`, or `spinel update --all`, every gem. Where Bundler 4 still warns that an update of everything will need `--all`, Spinel takes no gems to mean all of them, as this table always said. `--all` with gems is Bundler's `Cannot specify --all along with specific options.`, exit 15. Gems named with no lockfile are Bundler's `This Bundle hasn't been installed yet. Run `spinel install` to update and install the bundled gems.`, exit 22, the command it names Spinel's; each must be a gem the lockfile locks, else Bundler's `Could not find gem 'name'.`, with `Did you mean ...?` as `DidYouMean::SpellChecker` suggests (`did_you_mean.rs`), exit 7. Every gem with no lockfile is `spinel install`.
- **What moves.** As Bundler's default, not `--conservative`: each gem named and every gem it depends on in the lockfile are unlocked, and each named one goes to the newest version a resolution with nothing locked allows it, even when that takes a gem that depends on it with it; every other gem keeps its locked version, newer versions or not. With no gems, every gem goes to the newest the Gemfile allows. No gem goes below its locked version unless a conflict takes it there.
- **After.** As `CLI::Update` warns, a named gem whose version did not change is `Bundler attempted to update name but its version stayed the same`, and one that went down `Note: name version regressed from A to B`, on stderr, after the install's lines.
- **Nothing half-written.** The lockfile is written last, once everything is linked; a failed resolution, fetch or link leaves it byte for byte as it was.
- `// ponytail:` `--conservative`, `--patch`, `--minor`, `--major` and `--group` are refused, `` `--option` is not supported by `spinel update` yet. ``, exit 15, and nothing is written; `--strict`, `--pre`, `--source`, `--ruby` and `--bundler` are not taken at all. Upgrade: `Definition`'s `conservative` unlock, `GemVersionPromoter`'s levels and the groups' gems named.

`crates/spinel-cli/tests/update.rs` runs it against the gems `tests/fixtures/update/build.sh` builds (rake, rake-dep, shared and other, each 1.0.0 and 2.0.0), served on 127.0.0.1, from the lockfile Bundler 4.0.20 wrote with only 1.0.0 published: `spinel update rake` moves rake, rake-dep and shared and leaves other at 1.0.0, `spinel update` and `--all` move all four, and each lockfile is the one `bundle lock --update` wrote for the same index (`tests/fixtures/update/bundler.sh` records them), byte for byte; again with nothing newer, Bundler's warning and nothing written; Bundler's errors for an unknown gem (its words and status as recorded), a near miss, named gems with no lockfile, `--all` with gems and the options not taken yet; and a `.gem` that cannot be fetched, each leaving the lockfile and the GEM_HOME as they were. `tests/locked.rs` replays `bundle lock --update` steps recorded by `locked.sh` (a step's `<n>.update` names the gems): rake alone, rackup with the Rack it reaches, then everything, over Sinatra's set, and nokogiri's six native builds then everything for `rails new`'s Gemfile on seven platforms.

### 12. Git and path sources

`gem "x", git: ...` (and `github:`, `gist:`, a `git_source` of the Gemfile's, a `git` or `github` block), `gem "x", path: ...` (and a `path` block) and the `gemspec` directive are Bundler 4's `Source::Git`, `Source::Path` and `Source::Gemspec` (#88). `crates/spinel-cli/src/local_source.rs` reads them, and `crates/spinel-cli/src/git_source.rs` runs `git`:

- **Sources.** Each dependency's `source` in the evaluator's JSON is one; equal ones are one source (`==`: a git source by its URI less a trailing `/`, its ref, branch, glob and submodules; a path source by the directory it leads to), path sources first, then git ones, each in the order first named (`SourceList#all_sources`). A `tag` with a `branch` or a `ref` is `AmbiguousGitReference`'s message. A rubygems source scoped to some gems (`source:`, a `source` block) is section 3's; a source of any other type is not taken yet: exit 2.
- **Gemspecs.** A source's gems are the gemspecs its `glob` (`{,*,*/*}.gemspec` unless given) finds, evaluated on the VM by `shims/gemspec_eval.rb` in a child `spinel`, as `Bundler.load_gemspec` evaluates one: from its own directory, against a copy of the top-level binding, its `loaded_from` set, then `validate(false)`; deeper files first, so a shallower gemspec of the same gem wins (`Source::Path#load_spec_files`). An error is Bundler's (``There was an error while loading `x.gemspec`: ...``, `The gemspec at ... is not valid. ...`). A gemspec runs code, as it does under Bundler; what it answers is checked before any of it becomes a path, a stub or a gemspec in the GEM_HOME: a name rubygems.org allows, executables that are plain file names, a `bindir` inside the gem, no line breaks.
- **Resolution.** Every gem a git or path source has comes from it alone: the gems the Gemfile pins to it, and the other gems it has, unless another source has one too, which is Bundler's `The gem 'x' was found in multiple relevant sources.` (`SourceMap#all_requirements`). Their specs stand in for the index's builds of those names, so the resolver chooses among them as among any, and the index is read for what they depend on; when nothing comes from it, it is not read at all. A gem pinned to a source that does not have it is `Could not find gem 'x' in <source>.` and `The source does not contain any versions of 'x'`, as Bundler words it. `// ponytail:` a conflict's explanation names the rubygems source for such a gem too. Upgrade with each source's name in the resolver's packages.
- **Git.** The system `git`, as Bundler runs it, never through a shell. `<home>/git/<base name>-<16 hex>` is a bare clone of the repository shared by every project, where Bundler keeps one per bundle (`cache/bundler/git/`). A locked revision is used as it is, and fetched only when the mirror does not have it; otherwise the mirror is fetched and `git rev-parse --verify` of the ref, branch or tag, or of `HEAD` (the remote's default branch) when none is given, is the revision, as `GitProxy#find_local_revision` finds it: an annotated tag locks the tag's own object, as Bundler does. Each revision is checked out once, into `<home>/store/git/<base name>-<revision>[-submodules]/checkout`, as `GitProxy#copy_to` checks one out: a clone of the mirror whose `origin` is the repository again, reset to the revision, its submodules updated when `submodules: true`. It is built in `store/tmp/` and renamed into place, so one that exists is complete, and its gemspecs are evaluated there and overwritten with `to_ruby`, as `serialize_gemspecs_in` leaves a checkout; the evaluation is kept beside it (`gemspecs-<16 hex of the glob>.json`), so a warm install evaluates nothing. A URI, ref, branch or tag that starts with `-` is refused before `git` runs, a URI follows `--` wherever `git` takes one, a lockfile `revision:` that is not a full object name is refused, and `GIT_DIR` and `GIT_WORK_TREE` are cleared as `with_clean_git_env` clears them. `// ponytail:` the mirror is a full clone, where Bundler clones `--depth 1` when it can; a remote that renamed its default branch is not followed; `bundle config local.<gem>` overrides are not read, as no Bundler setting is. Upgrade with `GitProxy`'s depth arguments and `follow_remote_default_branch`.
- **Path.** Read where it is, every run, as Bundler reads it, and never copied: the store has nothing of it. Its `remote:` in the lockfile is the path relative to the project (`lockfile_path`); a directory that is not there is ``The path `...` does not exist.`` `// ponytail:` a path with no gemspec is not given the stand-in gemspec Bundler makes from a `name` and `version`.
- **`gemspec`.** The directive's gemspec is evaluated as `Dsl#gemspec` evaluates it, the `{,*}.gemspec` at its path, the one named with `name:`: its gem is added to the Gemfile pinned to a path source at that path, and its development dependencies in `development_group` (`development` unless given), with Bundler's errors for none and for more than one gem. A gem the Gemfile lists itself keeps its own line. `// ponytail:` they come after the Gemfile's own gems, where Bundler adds them where the directive is. Upgrade by having the evaluator mark its place.
- **With a lockfile** (section 3, "Locked preferences"). A source the lockfile has is the lockfile's (`replace_sources!`), and a Gemfile whose sources are not the lockfile's is `the list of sources changed`. A git source stays at its locked revision, which costs no fetch once the mirror has it, until it is let go: on an update of every gem, or of gems that unlock every gem the lockfile has from it (`converge_locked_specs`), as `spinel update widget` unlocks widget and what it reaches; its ref is then read again. `spinel update` does not warn that such a gem's version stayed the same, as its source is no longer the one it was locked from (`identifier`). A path source is read again every run: a spec the lockfile has from it that it no longer has, with the same dependencies, or Gemfile gems pinned to it that are not those the lockfile pins there, is `the gemspecs for path gems changed` (`converge_paths`); a locked spec takes the dependencies its gemspec has now, and one it no longer has is unlocked (`converge_specs`). `--frozen` lists a gem whose source is not the lockfile's under `You have changed in the Gemfile:`.
- **The lockfile.** `GIT` and `PATH` sections as `to_lock` writes them, sorted by `identifier` and before the `GEM` section (`SourceList#lock_sources`), each with the specs of the gems it provides; `!` on the Gemfile's gems pinned to one; and a `CHECKSUMS` line with no digest for each of their specs, as Bundler writes them.
- **The GEM_HOME** (section 5). A git or path gem is linked where its source has it: `gems/<full name>` is a symlink to the directory of its gemspec, in the checkout or the path, `specifications/<full name>.gemspec` its evaluated gemspec's `to_ruby_for_cache`, and `bin/` has stubs for its executables, so `require` finds it as any installed gem. `bundler/gems/<base name>-<12 digits of the revision>` is a symlink to each git checkout, where `Source::Git#install_path` looks under `BUNDLE_PATH`, and the scope views link `bundler/` too, so CRuby's `bundle exec` and `bundle install` find it with no checkout of their own; one into the store that no source names any more is removed.

`crates/spinel-cli/tests/git_path.rs` makes a git repository at test time from `tests/fixtures/git_path/widget-<version>/`, committed with a fixed identity and date, puts `gadget/` beside the project as a path gem, serves `shared` on 127.0.0.1, and compares each lockfile and Gemfile with what Bundler 4.0.20 wrote for the same steps (`tests/fixtures/git_path/bundler.sh`, opt-in): a branch and a path installed, locked, loaded, and installed again with nothing to do, the path gem changed in place with no install; a locked revision kept while `main` moves on, and Bundler's lockfile installed `--frozen`, byte for byte, by a Spinel home that has never seen the repository; `spinel update widget` moving the revision; a path gemspec's version raised, refused `--frozen` in Bundler's words and then locked; `spinel add widget --git`; a `gemspec` Gemfile; and a repository, a branch that looks like an option, a gem and a path that cannot be read, each writing nothing. Measured by hand beside it: CRuby's Bundler 4.0.20 runs `bundle exec` on what `spinel install` leaves and `bundle install` leaves its lockfile as it was. Bundler 4.0.20's `bundle lock --update widget` locks widget 1.1.0 at the old revision, where `bundle update widget` moves both; `spinel update` is `bundle update`, so `bundler.sh` records that.

## Commands

| command | does |
|---|---|
| `spinel install [--frozen]` | resolve (respecting lock) + install. `--frozen` errors if lock would change (CI). Section 8. |
| `spinel add <gem>[@req]... [--group dev] [--git url]` | write a `gem` line into the Gemfile where `spinel_ast` finds its place, then install; nothing is written if that fails. Section 9. |
| `spinel remove <gem>...` | take each gem's `gem` lines out of the Gemfile, and a `group` block that leaves empty, then install with the lockfile held, so only it and what only it needed leave the lock; nothing is written if that fails. Section 10. |
| `spinel update [gem...] [--all]` | unlock the gems named, and what they depend on, or all of them, then install; nothing is written if that fails. Section 11. |
| `spinel x <gem> [args]` | see cli.md |
| `spinel outdated` | phase 5 |

`bundle exec foo` has no equivalent because `spinel run foo` and `spinel x` already set up the environment; `.spinel/gem_home/bin` is on `PATH` inside `spinel run`.
